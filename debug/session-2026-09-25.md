## 1. 结论速览

| 项目 | 结论 |
| --- | --- |
| 根因 | **BLE 绑定的两半不一致**：板子这半被「绑定代次迁移」清掉了，Windows 那半还留着旧 LTK。链路永远加密不了，桌面端的 HID 写入被本地拒掉。 |
| 为什么「十多分钟后就好」 | Windows 会自己修这条坏记录，但按它自己的节奏走。**实测 9 分 40 秒**（09-25 02:46:21 → 02:56:01）。 |
| 为什么「重启后又失效」 | 每次重新烧录都触发了绑定迁移（`kBondRevision` 被反复加一），把板子那半又清空一次。 |
| 修了什么 | ① 默认**不再自动清绑定**；② 连接时**不再发 SMP Security Request**（实测会让旧绑定状态下 16 ms 断一次）；③ 连接日志增加 `bonds=N`，一眼看出绑定是否还在。 |
| 还需要做一次 | 清掉 Windows 侧旧记录 + **重新配对一次**。之后重启/重连都应立刻可用。 |
| **第二轮（09-25 晚，见第 10 节）** | 改完额度重烧后症状一样，但**根因换了**：这次是**主机侧 GATT 枚举停在半路**（只读了电量+配额，从没读 HID），桌面端连设备都看不见。**固件无关，重烧无用**；`python tools/ble_enum_guard.py --fix` 切一次无线电即修复，且复位板子不再复发。 |

### 2.4 板子侧串口（决定性证据）

2026-09-25 复现，固件在连接事件里主动发 SMP Security Request 时：

```text
I (5011) ble: connected peer e0:0a:f6:80:71:d2
I (5011) ble: security requested id=0
I (5011) ble: host connected id=0 bonds=0          ← 板子这半是空的
W (5026) BT_APPL: bta_dm_ble_smp_cback remove bond,rsn 102, BDA:0xE00AF68071D2
E (5027) BT_BTM: Device not found
W (5027) BT_HCI: hcif disc complete: hdl 0x1, rsn 0x13
I (5028) ble: host disconnected id=0 reason=0x13   ← 16 ms 就断
W (5029) ble: pairing failed reason=0x66           ← 0x66=102=ESP_AUTH_SMP_CONN_TOUT
```

三个结论：

1. `bonds=0` 而主机仍在连 → 两半不一致，实锤。
2. 主机**根本不回答** Security Request（`rsn 102` 是本地超时），直接拆链。
3. 这个循环可以无限持续 → **主动请求安全在这条路径上只会更糟**。

## 3. 根因链

```text
某次重新烧录 → kBondRevision 被加一 → 板子在启动时清空自己的绑定
                                      ↓
                        Windows 仍持有旧 LTK（按地址存）
                                      ↓
        主机连上后想用旧 LTK 恢复加密，板子拿不出对应密钥
                                      ↓
        链路始终不加密 → HID 报告特征（要求加密）的写入被本地拒掉
                                      ↓
        Codex 桌面端报 WRITE_FAILED / 0x57 → 界面显示「已连接，功能受限」
                                      ↓
        Windows 按自己的节奏（实测 ≈10 分钟）修好记录 → 一切正常
                                      ↓
        下次烧录再清一次绑定 → 回到「功能受限」
```

关键代码位置：`main/codex_ble.cpp`

- `kBondRevision` / `clearIncompatibleBondsOnce()`（绑定代次迁移）
- `ESP_GATTS_CONNECT_EVT` 分支（安全请求）
- `s_cccd` / `s_batteryCccd`（CCCD 预置）

## 4. 本次改动

### 4.1 `main/codex_ble.cpp`

| # | 改动 | 原因 |
| --- | --- | --- |
| 1 | 绑定迁移改为**默认关闭**：`CODEX_BLE_BOND_REVISION` 默认 `0` | 常规烧录绝不能毁掉已经配好的绑定；这正是「重启后又失效」的来源。需要逃生时再显式定义该宏。 |
| 2 | 连接事件里**不再调用** `esp_ble_set_encryption()`，改为 `CODEX_BLE_SECURITY_ON_CONNECT` 宏（默认 0） | 实测：绑定不一致时 16 ms 一次断连循环，比不调用更糟；绑定健康时主机自己会在 ACL 建立时用 LTK 完成加密，不需要我们催。 |
| 3 | 连接日志增加 `bonds=N` | 一行就能判断绑定是否还在，不用再翻寄存器。 |
| 4 | 注释里写清两种情况的实测数据 | 防止后续 agent 再把这两条「看起来更主动」的改动加回来。 |

### 4.2 未改动但需要知道的既有开关

| 开关 | 位置 | 默认 | 说明 |
| --- | --- | --- | --- |
| `CODEX_BLE_REQUIRE_ENCRYPTION` | `codex_ble.cpp` | `1` | HID 报告特征要求加密。这是让主机「必须配对」的触发点，**不要关**。 |
| `CODEX_BLE_HID_CCCD_PREARMED` | `codex_ble.cpp` | `1` | HID input CCCD 预置为使能。关掉的话通知会被本地静默丢弃（连上了但按键没反应）。 |
| `CODEX_BLE_TRACE` | `codex_ble.cpp` | `0` | 打开后配合 `CONFIG_LOG_MAXIMUM_LEVEL_DEBUG=y` 可看 HCI/ATT/SMP 细节。 |

### 5.1 追加：`28:84:85:B2:1C:73` 的记录已经修不回来了（2026-09-25 12:10 实测）

第 1 步的 `UnpairAsync` 清掉记录之后，出现了新的、更隐蔽的坏状态。板子串口每 22 秒一轮：

```text
I (26256) ble: pairing complete                    ← 加密是建立成功的
I (26316) ble: connected peer e0:0a:f6:80:71:d2
I (26317) ble: host connected id=0 bonds=1         ← 绑定也在
I (26556) ble: mtu id=0 value=517
I (27284) ble: read id=0 handle=68 offset=0 long=0  ← 配额服务
I (27659) ble: read id=0 handle=63 offset=0 long=0  ← 电池
I (27778) ble: read id=0 handle=65 offset=0 long=0
I (27869) ble: read id=0 handle=64 offset=0 long=0
W (25497) BT_HCI: hcif disc complete: hdl 0x1, rsn 0x8   ← 空闲 22 秒后被拆
```

三条判据说明这条地址已经废了：

1. **主机从来不碰 HID 服务**（句柄 55–62 一次都没有 read），只枚举电池和配额 →
   Windows 根本没有绑定 HID-over-GATT 驱动。
2. `tools/hid_caps.py` 一直报 `no HID interface is present`；
   `tools/ble_host_diag.py` 里连 `BTHLE\DEV_288485B21C73` 节点都不存在。
3. WinRT 那边却是 `conn: Connected` + `paired: false` + `canPair: false` ——
   缓存说它连着，设备树却不存在，且拒绝重新配对。

更麻烦的是：**被连接期间板子会停止广播**（`startAdvertising()` 在 `g_connectionCount > 0`
时直接返回），所以 Windows「添加设备」列表里也扫不到它——这就是「电脑蓝牙搜索不到
Codex Micro」的直接原因。

#### 处理：换一个 Windows 从未见过的地址

已改为 `kBondGeneration = 0x5F`（广播 `28:84:85:B2:1C:75`），
同时把 `CODEX_BLE_BOND_REVISION` 设为 `6`，让板子把旧的对端绑定也清掉一次
（否则那条旧 LTK 会干扰新地址的首次配对）。

新地址在 Windows 侧没有任何记录 → 主机不会自动连 → 板子**持续广播** → 能被扫到、能配对。

> ⚠️ `kBondGeneration` 只在这个场景下动，配对成功后**不要再改**。
> 地址一改，Windows 的 `BthLEEnum` 节点就失效，而那个节点才是「主机自动重连」的依据。

## 6. 关于「额度同步，官方有没有更好的办法」

### 6.1 官方通道是什么

Codex 桌面端自带 **Codex Micro 支持**（日志里的 `CodexMicroService`），它直接通过
Windows 的 HID 设备节点（`node-hid`）和设备说话，推的是：

| 方法 | 方向 | 内容 |
| --- | --- | --- |
| `v.oai.rgbcfg` | 主机 → 设备 | 灯光配置 |
| `v.oai.thstatus` | 主机 → 设备 | 6 个会话状态 |
| `device.status` | 主机 → 设备 | 查询固件版本、当前布局、电量 |
| `v.oai.hid` / `v.oai.rad` | 设备 → 主机 | 按键、摇杆 |

**这条通道里没有额度（rate limit）。**

### 6.2 结论

- **官方没有 Windows 端伴生程序。** 上游 `huaxx-lab/codex-micro-stopwatch` 的 Bridge 只有 macOS，
  而且它的职责是语音回退、窗口唤醒、摇动清空、旋钮模式同步，同样不推额度。
- 表盘上的**额度环是本移植版自己加的功能**，走私有 BLE 特征
  `7f0d4e66-2ac2-4a71-bfbe-4ef61a0e5c01`（写 `…5c02`）。它必须由本机程序读额度再写进去，
  没有官方 API 可以替代。
- 所以「更好的办法」不是换数据源，而是**不用手工启动**。

### 6.3 建议做法

数据源已经是当前最优组合（`windows_companion.py` 内部逻辑）：

```text
① http://127.0.0.1:8787/quota   ← 本机已在跑的 usage 服务，毫秒级返回（本机实测可用）
   ↓ 重排成 App Server 的形状
② codex app-server --listen stdio://  ← 兜底：复用本机 Codex 登录态
   ↓ initialize → initialized → account/read → account/rateLimits/read
   ↓ 取 windowDurationMins == 10080 的周窗口
   ↓ BLE 写入私有特征
```

让它常驻，而不是每次手动开一个终端：

```powershell
# 方案 A：任务计划程序，登录时启动（推荐）
schtasks /create /tn "Codex Micro Quota" /sc onlogon /rl limited ^
  /tr "\"D:\Espressif\python_env\idf5.4_py3.12_env\Scripts\python.exe\" ^
       \"C:\path\to\windows_companion.py\" --device-address 28:84:85:B2:1C:73 --watch --interval 60"

# 方案 B：启动文件夹放一个 .cmd（同上内容，最简单）
```

> 附带好处：`--watch` 会一直挂着一条 GATT 客户端链路。本机蓝牙网卡（Realtek）默认允许
> 「空闲时关闭以省电」，没有客户端时链路会每 32.88 秒被拆一次；常驻的伴生程序正好把它顶住。
> 想彻底解决可以管理员运行 `python tools/bt_power_repair.py --apply`。

## 7. 排障手册（下次再遇到时按顺序走）

### 7.1 先判断卡在哪一层

| 板子串口 | 含义 | 下一步 |
| --- | --- | --- |
| 有 `host connected` 但 `bonds=0` | 绑定两半不一致 | 第 7.2 节 |
| 有 `host connected` + `pairing complete` + `RPC method=…` | 正常 | 看桌面端设置页 |
| 一条 `host connected` 都没有 | 主机没发起连接 | 第 7.3 节 |

### 7.2 绑定不一致

```powershell
& $PY tools/ble_host_diag.py 28:84:85:B2:1C:73     # 看主机侧节点与配对状态
& $PY windows_companion.py --device-address 28:84:85:B2:1C:73 --repair-pairing -v
# 然后在「设置 → 蓝牙」里重新配对一次
```

### 7.3 主机不发起连接

```powershell
& $PY tools/bt_radio_toggle.py --status   # 只看状态
& $PY tools/bt_radio_toggle.py            # 关 → 4 秒 → 开（会断开所有蓝牙设备几秒）
```

Windows 蓝牙栈在长时间反复连断之后会假死，关开无线电是唯一不需要管理员的解法。

### 7.4 常用工具

| 工具 | 用途 |
| --- | --- |
| `tools/hid_caps.py [--write-test]` | 查 Windows 为这块板子推导出的 HID 能力（应为 `UsagePage=0xFF00`、`input=64B output=64B`） |
| `tools/hid_rpc.py --method sys.version --listen 5` | 绕开桌面端，按它的分帧直接发一条 RPC |
| `tools/ble_scan.py` | 列出 Windows 已知的 BLE 设备 |
| `tools/ble_host_diag.py <addr>` | 读 PnP 节点 + 注册表绑定记录 |
| `tools/bt_power_repair.py [--apply]` | 关掉网卡「允许关闭以省电」（需管理员） |
| `boot_capture.py COM5 120` | 复位并从头抓串口（不漏开机第一行） |

### 7.5 踩过的坑

- **不要用系统 python**：没有 `pyserial`。用 `D:\Espressif\python_env\idf5.4_py3.12_env\Scripts\python.exe`。
- **`tools/serial_capture.py` 会拉 DTR/RTS**，可能顺手复位板子。要抓开机第一行用 `boot_capture.py`。
- **启动日志里的地址是基址 MAC**，不是广播地址。广播地址 = 基址 + 2。
  本机出厂 MAC `28:84:85:b2:1c:2c`，`gen=0x5D` → 基址 `…:1c:71` → 广播 `…:1c:73`。
- **不要盲目加 `esp_ble_set_encryption()`**：peripheral 恒为 slave，它必然 fall through 到
  `SMP_Pair()`，在绑定不一致时会把链路打进 16 ms 的断连循环。已在代码注释里记下实测数据。

### 结论性的两条「不要」

1. **不要**为了「主动缩短连接→可用之间的空窗」而在连接事件里调 `esp_ble_set_encryption()`。
   绑定健康时不需要它；绑定不一致时它把链路打成 16 ms 循环，比什么都不做更糟。
2. **不要**在常规烧录里清绑定。绑定迁移只应该是显式的、一次性的逃生手段。
   每一次误触发，代价都是用户重新配对 + 可能长达 10 分钟的功能受限。

### 10.3 机制（为什么"重烧"正好会触发它）

```text
idf.py flash → esptool 硬复位板子 → 主机侧的 GATT 枚举被从中间打断
                                      ↓
          Windows 留下"这块设备只有电量 + 配额"的枚举记录（按地址存）
                                      ↓
   之后每次重连都拿这份记录作答 → 永远不去读 HID 服务
                                      ↓
       BthLEEnum 不建 {00001812-…} 子节点 → 没有 HID 接口
                                      ↓
   桌面端 hidTopologyWatcher 等的是"HID 拓扑变化"，没有变化 → 永远静默
                                      ↓
             表现为「已连接，功能受限」，而且等十分钟也不会好
```

`kBondGeneration` 换地址之所以当时"有效"，也是因为它顺带让主机丢掉旧记录——
代价是要重新配对。**切无线电能达到同样效果而不动地址、不动绑定**，所以它是首选。
